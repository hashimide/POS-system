Summary

  • Goal: a merchant installs our Shopify app, approves once, and sees a view-only OTTO dashboard inside Shopify — the same one WordPress users get. Uninstalling cleans everything up.
  • Today the app is forgetful and unsafe: it remembers nothing about the store, asks the backend "who is this store?" on every page using only the store's web address, and shows the merchant's full account through a 180-day login pass sitting in a web address.
  • The fix: give the app a memory. One safe handshake per store, then the app keeps its own revocable key and the OTTO project ID, and never asks "who am I?" again. No login pass ever reaches the browser.
  • Order of work: first close two open doors in the backend (urgent, small), then the stored connection and view-only dashboard, then finish the log-in path and the pixel, then clean up old code.
  • Lazaro (OTTO PM) approved the plan on 6 Nov: one approval for the merchant, proof via Shopify's short-lived pass, OTTO receives the store's key so it can write fixes into the store, projects use the store's real domain.
  • Where we are: test payments work safely, the app already remembers each store's real domain and deletes its record on uninstall. The two security lock-downs are not started — that's the next step.

Words used in this document

Plain words for the few technical things we can't avoid naming:

The app
Our Search Atlas app inside Shopify admin (the thing the merchant installs).
The backend
Search Atlas's own servers — they own accounts, plans and billing.
Login pass
A long-lived pass (180 days) that opens the merchant's whole Search Atlas account. Today it leaks into web addresses. Goal: it never leaves our server.
Store key
A per-store pass our backend can mint and revoke. The app's new way to prove who it is — like a password we can change per store.
Proof pass
A Shopify-signed pass that lives about one minute and proves "this request really came from this store". Single-use, nothing secret kept.
Long-lived store key
The master key Shopify gives our app for a store (install it once, use it forever). Great for working on the store, too precious to send around just to prove identity.
Handshake
The one-time connect step: the app proves which store it is, and receives its store key, OTTO project ID and dashboard address.
Real domain vs internal address
Shoppers see yourstore.com (the real domain). Shopify internally also gives every store a permanent something.myshopify.com address. Same store, two addresses, different jobs.
Public share code
A harmless code that unlocks the view-only OTTO page for one project. Safe to show in the browser.
Theme app embed
The modern way to add a script to a Shopify store: a block the merchant switches on once in their theme editor.

The goal

What success looks like

  • A merchant installs the app, approves once, done — no second OTTO login.
  • Inside Shopify they see the view-only OTTO dashboard. To change anything, they click "Open Search Atlas" in a new tab.
  • Stores that don't have an OTTO project yet get a clear, friendly screen — and the dashboard appears by itself once they create one.
  • Uninstall revokes everything and leaves nothing behind.
  • Stores already connected move to the new system by themselves — no merchant action.

What we are deliberately NOT building

  • No rebuild of billing or the plans page.
  • No automatic OTTO project creation for log-in stores (it spends the merchant's paid quota and we might pick the wrong domain).
  • No interactive dashboard inside Shopify — looking only.
  • The pixel / theme app embed is agreed as a later topic, not now.
  • Shopify's big key deadline (Jan 2027) is tracked as its own separate work item.

How the app works today

Every single page load

  1. The app asks the backend "who is this store?" — sending only the store's web address.
  2. The backend answers with a brand-new 180-day login pass and a dashboard address.
  3. The app opens that address inside Shopify — putting the login pass right into the web address of the page.

So the app has no memory, every page costs an extra round trip, and the most powerful pass we have travels through the browser on every load.

Two ways a store gets connected

Way 1 — the merchant subscribes

  • They pick a plan in the app and approve the payment in Shopify.
  • The backend creates their Search Atlas account, the subscription, and an OTTO project.
  • …but the new project's ID is thrown away, and the project is set up for the wrong address (the internal one, not the real domain).

Way 2 — the merchant logs in

  • They log in with an existing Search Atlas account.
  • The store gets linked to that account — and that's all.
  • No OTTO project, no pixel, no store details saved. OTTO never runs for them, even if they later create a project themselves.

The tracking pixel

OTTO's pixel is added to the storefront using an old script-planting method that Shopify rejects since 1 October 2026. New stores get no pixel at all, and existing planted scripts stop working entirely on 1 March 2027. The replacement is a theme app embed the merchant switches on once.

For comparison: how WordPress does it

The WordPress plugin already works the way we want: it stores an encrypted per-site key and the OTTO project ID, trades the key for a short-lived pass on the server (the browser never sees it), and shows the public view-only dashboard page. We are bringing Shopify up to the same design.

Act on the two critical rows now. They are small to fix, urgent, and independent of everything else in this plan. That fix is Step 1 below — and nothing has been built for it yet.

The plan, step by step

Four steps, each shippable on its own. App-side and backend-side work inside a step can be built at the same time; the app side is only switched on after the backend side is live.

Step 1Close the open doors — now

Backend: start checking that the caller really is the store before answering the "who is this store?" question, and stop saving passes that strangers send. App: stop putting the store's key into web addresses (already written, waiting for release).

Done when: a wrong or missing key for a linked store gets rejected and nothing changes in the database — while the real app keeps working for real merchants.

Step 2Stored connection + view-only dashboard

Backend: the handshake endpoint, room on the store's account for the project ID and real domain, and a disconnect endpoint. App: the new database columns, the encryption helper, the connection module, the three-state screens, the view-only dashboard, and key revocation on uninstall.

Done when: a linked store with a project sees the public dashboard; no login pass appears anywhere the browser can see; the second page load makes no identity call to the backend; uninstall revokes the key.

Step 3Log-in stores complete, payment path fixed

Backend: save real store details for log-ins; the pixel loads exactly one project, by ID; new paying stores get one project for their real domain with the ID saved on both sides; fix the notification-genuineness check before relying on it more. App: the full "create your project" screen with automatic pick-up, and the pixel theme app embed.

Done when: a log-in store that creates its project sees the dashboard after "Check again" — no second login — and its storefront loads exactly one pixel through the activated embed. Old log-in stores get their missing store details filled in by a one-time backfill.

Step 4Clean-up

Backend: stop returning login passes and dashboard addresses to the app entirely. App: delete the dead code.

Done when: no answer from the backend to the app contains a login pass, and the old paths are gone.

How a store gets connected (the handshake)

One safe exchange covers every situation: new installs, merchants who pay, merchants who log in, and stores that were connected before this work.

1
The merchant approves once. Our app's own Shopify approval screen asks for read/write products, read/write content and read themes. There is no separate OTTO approval — Lazaro confirmed OTTO rides on ours.
2
The app proves which store it is. It sends Shopify's short-lived proof pass (lives about a minute, signed with our app's own secret — which the backend already holds). The long-lived master key is not sent just to prove identity — Lazaro's explicit decision.
3
The backend hands over the credentials. It finds the store's Search Atlas account, makes a fresh revocable store key named for that store, and returns: the key, the OTTO project ID (if one exists), the project's domain, and the right dashboard address (works for whitelabel brands too). If the store isn't linked to any account, it says so.
4
OTTO gets its own access. In the same step, the store's long-lived key is handed to OTTO's Connector Gateway — OTTO's existing door into every other system (WordPress included) — so OTTO can write fixes into the store. The exact details still need to be agreed with Arslan Abbas.
5
The app saves its one row for the store: the key (encrypted), the project ID, the real domain. From then on it identifies itself with the key and never asks "who is this store?" again.

One side effect to agree on: minting the new store key switches off the merchant's oldest-style API key, which they might use in other tools. The WordPress connect flow already behaves this way. Product/backend needs to confirm that's acceptable.

The three store states

After the handshake, the app decides what to show from its own record — never by asking the backend who the store is.

no record yet Not linked
  • Show today's connect screen: "Log in" or "Subscribe to a plan".
  • First, quietly try the handshake once — this picks up existing stores and payment returns with no extra clicks.
record, no project Linked, no project
  • A friendly notice: "Create your OTTO project for yourstore.com in Search Atlas."
  • Buttons: "Open Search Atlas" (new tab, normal sign-in) and "Check again".
  • Re-checks automatically, at most once a minute while the screen is open.
  • Several matching projects: show a picker (exact domain matches only).
record + project Ready
  • Show the view-only OTTO dashboard.
  • "Open Search Atlas" for edits, in a new tab.
  • Plans and billing pages keep working exactly as today.

Why we never auto-create the project for log-in stores: it spends the merchant's paid project quota, we'd have to guess the domain (usually wrongly), and many of them already have one — we'd create duplicates. WordPress works the same way: create the project first, then connect. To keep it from feeling like a dead end, the store is linked immediately and the dashboard appears by itself once the project exists.

Where each piece of information lives

InformationLives inWhy
Store keyApp database, encryptedOne per store, revocable on its own. Proves who we are without the "just a domain" trick.
OTTO project IDApp database and the backendThe app needs it for the dashboard; the backend needs it so the pixel loads exactly one project.
Dashboard addressApp databaseChosen once at connect time; respects whitelabel brands.
Login passApp server memory onlyRefreshed before it expires. Never in the database, a web address, a log, or the browser.
Public share codeApp server memory, 1-hour cacheCheap to fetch again; safe for the browser to see.
Plan, charges, subscription statusBackend (unchanged)Billing stays the backend's job. Only the plans and cancel pages ask about it.

Nothing personal is stored. The new record holds no customer data — just the store address, its key, its project ID and its real domain. It is deleted on uninstall and on Shopify's data-deletion request.

Two addresses per store

Every store has a permanent internal address (something.myshopify.com) — the right ID for talking to Shopify — and the real domain shoppers actually visit (yourstore.com). Today everything uses the internal one, which is why OTTO ends up working on the wrong site.

  • The real domain becomes the source of truth for OTTO. Lazaro confirmed: projects use the store's primary domain.
  • The app reads it once at connect time, re-checks when the merchant clicks "Check again", and otherwise at most once a day. Never on every page load.
  • Development stores have no custom domain — their internal address is stored as-is and everything behaves exactly like today. No errors, no empty-domain projects.
  • If the real domain changes later, warn the merchant. Never create or re-point anything automatically.
  • Existing stores are untouched on the backend; the app simply reads the real domain into its own record.

The pixel story

  • Old way (dead): the app planted a script on the storefront directly. Shopify rejects new ones since 1 October 2026 and stops injecting existing ones on 1 March 2027.
  • New way: a theme app embed — a block the merchant switches on once in their theme editor. Until they do, the pixel stays off; our screens will include a clear "Activate pixel" step.
  • Never run both at once — the pixel would load twice. An old planted script is only removed after that store's embed is confirmed active.
  • Step 3 work, after the connection itself is solid.

Uninstall and clean exit

  1. The store's key is revoked — and the revocation call itself requires that key, so only the real app can do it.
  2. The app drops its cached login pass. (Revoking the key alone isn't instant for passes already minted from it, so the cache drop matters.)
  3. The app's record for the store is deleted — already working today, even in the awkward case where the merchant's session is already gone.
  4. Reinstall goes through the handshake fresh and receives a brand-new key.

Old stores keep an eye on: the cleanup must run even when the merchant's session disappeared before the uninstall arrived (a known trap — the current handler gives up early in that case). It gets checked during Step 2 testing.

Existing stores move over by themselves

  • No batch job, no merchant email, no action needed.
  • A connected store's first open of the new app version simply does the handshake and creates its record (marked internally as a "backfill").
  • Older paying stores whose project ID was never saved land in "Linked, no project" and link their project with one click of "Check again" — which matches on the exact domain only and creates nothing.
  • The backend's stored data for existing stores does not change.
  • Merchants running an older app version keep working until Step 4 removes the old answers; Shopify updates all merchants at once, so the overlap is short.

How we'll test

Safety first: dev stores only, never a real charge on production. A dev store must be on the backend's test-payment list — a store that isn't gets a real charge. And set a valid phone number on the dev store first, or the payment confirmation breaks.

Every case we will walk through before calling any step done:

  • Wrong or missing key for a linked store → rejected, nothing saved.
  • Someone else's key on the log-in flow → rejected, no link created.
  • Fresh install + log-in, no project yet → friendly notice, no pixel planted.
  • Merchant creates the project, clicks "Check again" → dashboard appears, one pixel loads.
  • Merchant has two similarly named projects → picker shows exact domain matches only.
  • Fresh install + pay (test charge) → one project for the real domain, ID saved both sides, merchant lands on the dashboard — not an error page. Re-opening the payment confirmation link creates nothing new.
  • Existing connected store opens the new app → its record appears by itself, nothing else changes.
  • Existing store whose project was made under the real domain → found by exact match and linked; nothing created, nothing overwritten.
  • Dev store without a custom domain → internal address stored as-is, behaves exactly like today.
  • Opening the app several times in a day → no extra domain reads.
  • Dashboard page, network log → no login pass, no store key — only the project ID and the public share code.
  • Public dashboard opened in a private window → nothing can be edited or approved.
  • Uninstall → key shows as revoked, record gone; reinstall receives a new key.
  • Server restart → first page load re-fetches once, no errors.
  • Whitelabel brand customer → their own dashboard address is used.
